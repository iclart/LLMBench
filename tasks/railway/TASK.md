## 1. 交付物与编译

- 你只能修改 `src/` 目录。评测时只取 `src/` 下的文件，其他目录的改动一律无效。
- 接口头文件 `include/ticket_system.h` 只读，不得修改；你需要实现其中的 `rail::TicketSystem`，并提供工厂函数 `rail::create_ticket_system()`。
- 官方编译命令固定为（压测器源码由评测方提供并一同链接）：

  ```
  g++ -O2 -std=c++20 -pthread -Iinclude src/*.cpp <压测器源码>
  ```

  - **允许**在源码里使用 `#pragma GCC optimize(...)` 和 `#pragma GCC target(...)`。
  - 只能使用 **C++ 标准库和 pthread**，不能引入任何第三方库或头文件。
  - 禁止用内联汇编发起系统调用。
- 官方评测在 Linux（x86-64，g++）上进行。Windows 可以用 MinGW-w64 g++ 以相同参数编译和自测，但成绩以 Linux 为准。

## 2. 世界模型

### 2.1 站点、线路、车次

- **站点**：编号 `0..station_count-1`。
- **线路**：一串有序的站点。不同线路可以共享站点，共享的站点就是**换乘站**；也有完全孤立、和其他线路没有公共站点的线路。
- **车次**：沿某条线路运行，停靠这条线路的一个站点子集（快车停得少，慢车停得多），也可能只跑线路的一段。
  - 每个车次停站数在 2 到 60 之间，同一车次不会两次停靠同一个站。
  - 车次的停站顺序就是它的行驶方向，同一条线路上两个方向的车次都有。

### 2.2 时刻表与车次日

- 每个车次有固定的时刻表，**每天都一样**。时刻表里的时间是“相对该车次**始发日** 00:00 的分钟数”，可能超过 1440（跨过午夜）。
  - 首站 `arrive == depart`，末站 `arrive == depart`，中间站 `arrive < depart`。
  - 沿车次方向，时间严格递增。
- 系统**预售 3 天**：第 0、1、2 天。一个**车次日**是 `(train, day)`，表示 `train` 在第 `day` 天从首站始发的那一趟。不同车次日的库存相互独立。
- **绝对时间** = `day × 1440 + 时刻表分钟数`。请求和返回里的时间都是绝对时间。

### 2.3 车厢与座位

所有车次编组相同，每个车次日 578 个座位：

| 车厢 | 席别 | 布局（`│` 是过道） | 排号 | 座位数 |
|---|---|---|---|---|
| 1 | 商务座 `Business` | `A │ C F` | 1–8 | 24 |
| 2–3 | 一等座 `First` | `A C │ D F` | 1–13 | 每节 52 |
| 4–8 | 二等座 `Second` | `A B C │ D F` | 1–18 | 每节 90 |

- **靠窗座位**：A 和 F。
- 过道把一排分成两个**同侧块**：商务座 `[A]`、`[C F]`；一等座 `[A C]`、`[D F]`；二等座 `[A B C]`、`[D F]`。

### 2.4 区间票

- 车次的第 `i` 站到第 `i+1` 站称为第 `i` 个**区间**。从第 `a` 站上车、第 `b` 站下车（`a < b`），占用区间 `[a, b)`。
- 同一车次日的同一座位，可以卖给多张占用区间**互不相交**的票。例如 A→C 卖出后，同一座位的 C→E 仍然可以卖。
- 一程之内，每位乘客从上车到下车**全程坐同一个座位**。

## 3. 接口

见 `include/ticket_system.h`。要点：

- `init(world)` 只调用一次，单线程，在其他任何调用之前。`world` 中的指针在引擎的整个生命周期内保持有效且不变。`init` 的耗时**上限 30 秒**。
- `init` 返回后，`query`、`book`、`refund` 会被**任意多个线程并发调用**。
- 所有请求和返回都是 POD 结构体，通过返回值 `Status` 报告结果，不要抛异常。

## 4. 换乘方案：`query`

`query` **只看时刻表，不看余票**。它的结果完全由世界数据和请求决定，评测时会逐条和参考实现比对，**必须完全一致**。

### 4.1 合法的方案

一个方案由 `n` 程组成（`1 ≤ n ≤ 3`，即最多换乘 2 次），第 `i` 程是车次日 `(train_i, day_i)` 从站 `from_i` 到站 `to_i`。方案**合法**当且仅当：

1. 每一程：`train_i` 存在；`0 ≤ day_i ≤ 2`；`from_i` 和 `to_i` 都是该车次的停站，且 `from_i` 在 `to_i` 之前。
2. 相邻两程：`to_i == from_{i+1}`（同站换乘），并且 `depart_{i+1} ≥ arrive_i + 30`（绝对时间）。
3. 起点、各换乘站、终点这 `n + 1` 个站**两两不同**。
4. 同一个车次日不能在方案里出现两次。

其中 `depart_i` 是第 `i` 程在 `from_i` 的绝对发车时间，`arrive_i` 是第 `i` 程在 `to_i` 的绝对到达时间。

### 4.2 查询的候选集

对请求 `(from, to, earliest, k)`，候选方案是满足以下条件的所有合法方案：

- 第一程从 `from` 出发，最后一程到达 `to`；
- 首程发车时间 `depart_0` 落在 `[earliest, D)` 内，其中 `D = (⌊earliest / 1440⌋ + 1) × 1440`，也就是**首程必须在 `earliest` 当天发车**；
- 后续各程的车次日只要在预售期内即可（第 0–2 天始发），到达时间可以落到第 3 天及以后。

### 4.3 去重

**车次日序列**相同的候选方案只保留一个：比较序列 `(arrive_0, arrive_1, …, arrive_{n-2})`，即各次换乘时下车的时间，保留字典序最小的那个，也就是“尽早换乘”。

### 4.4 排序与返回

去重后按以下顺序排序，依次比较：

1. 程数 `n` 从少到多（换乘次数最少优先）；
2. 最终到达时间 `arrive_{n-1}` 从早到晚；
3. 首程发车时间 `depart_0` 从**晚**到早（等得少的优先）；
4. 车次日序列 `(train_0, day_0, train_1, day_1, …)` 按字典序从小到大。

返回前 `k` 个；不足 `k` 个就全部返回，候选为空时返回 `count = 0`、`Status::Ok`。每程的 `depart` 和 `arrive` 都要填绝对时间。

### 4.5 非法请求

以下情况返回 `Status::Invalid`：`from` 或 `to` 不存在；`from == to`；`earliest` 不在 `[0, 4320)`；`k` 不在 `[1, 5]`。

## 5. 订票：`book`

### 5.1 校验

以下情况返回 `Status::Invalid`，并且**不改变任何状态**：

- `leg_count` 不在 `[1, 3]`；
- 各程组成的方案不满足 4.1 的合法性条件（注意：`book` **没有** 4.2 中“首程当天发车”的限制）；
- `seat_class` 不是三种席别之一；
- `passenger_count` 不在 `[1, 5]`。

`Invalid` 的判断优先于 `SoldOut`。

### 5.2 原子性

- 如果**每一程**都有至少 `passenger_count` 个该席别的座位，在这一程的整个占用区间上空闲，就必须出票：返回 `Status::Ok`，为每程每位乘客分配座位。
- 否则返回 `Status::SoldOut`，并且**不占用任何座位**。不允许只订成部分程。
- **只要有座就必须出票**：座位够却返回 `SoldOut`，判为错误（假阴性）。

### 5.3 出票

- `out->order_id`：非零，在引擎整个生命周期内唯一，退票后也不重复使用。
- `out->seats[i][p]`：第 `i` 程第 `p` 位乘客的座位。同一程内各乘客的座位必须互不相同，席别必须正确。同一位乘客在不同程可以坐不同座位。

### 5.4 座位偏好（软约束）

偏好不影响能否出票，只影响质量分。

- **靠窗**：`window[p]` 为真的乘客，分到 A 或 F 座即算满足。
- **同行**：`together` 为真且 `passenger_count ≥ 2` 时，按每一程分别判断，记 `n = passenger_count`，`m` 为该席别最大同侧块的座位数（商务 2、一等 2、二等 3），`w` 为每排座位数（商务 3、一等 4、二等 5）：
  - `n ≤ m`：全部在同一车厢、同一排、同一个同侧块内，且座位连续；
  - `m < n ≤ w`：全部在同一车厢、同一排；
  - `n > w`：全部在同一车厢，且所用排号最大值与最小值之差不超过 1。
- 偏好不保证一定能满足；座位碎片化时满足不了是正常的。

## 6. 退票：`refund`

- 只支持**整单退票**：一次退掉该订单的所有程、所有乘客，座位立即释放，后续订单马上可以买到。
- 订单存在且尚未退过，返回 `Status::Ok`；订单号不存在、已经退过、或者是 0，返回 `Status::NotFound`。
- 多个线程同时退同一张订单时，**恰好一个**返回 `Ok`。

## 7. 并发要求

- `query`、`book`、`refund` 必须是**线程安全**且**可线性化**的：每次调用都必须看起来在它开始和返回之间的某个瞬间原子地生效。
- 裁判会记录每次调用的开始和结束时间，并按可线性化的标准检查：超卖、座位区间冲突、多程不原子、重复退票成功、假阴性。对假阴性的判定是**保守**的：只有在你的 `SoldOut` 调用期间，裁判能确定座位**始终**充足时，才会判错。静默阶段是单线程的，裁判会按你自己已经分配出去的座位**精确**判定：有座却返回 `SoldOut` 就是错误。
- 静默阶段之后还有**审计阶段**（同样单线程）：对本轮中订票失败的多程订单、以及被退掉的订单所涉及的每一程区间，反复订票直到售罄。如果你的引擎在失败回滚或退票时“丢”了座位（座位被占着却不属于任何有效订单），这里会被精确地判为假阴性。
- 评测时会用 ThreadSanitizer 编译你的代码跑小规模负载。**任何数据竞争都会导致总分为 0**，包括“只是统计计数器”的那种竞争。请用 `std::atomic` 或锁保护所有共享数据。

## 8. 资源限制与禁止事项

- 评测机为引擎提供 **4 个 CPU 核**。压测线程数分别为 1、4、16。你可以自己创建线程，但只有这 4 个核。
- **内存上限 1.5 GB**，超限进程会被杀掉，按崩溃处理。
- 禁止：读写文件、访问网络、创建子进程、在多次运行之间缓存任何东西、读取压测器或裁判的内部状态、识别负载内容做特判。
- 不要向 stdout 输出任何内容。stderr 的输出会被丢弃，并且计入耗时。

## 9. 评测与计分

### 9.1 负载

- 负载由大量“用户”组成：查询后订第一个方案，失败就改订下一个；有的用户只查不买；有的会随机退掉别人订好的票；还混有少量非法请求和重复退票。
- 三个场景：
  1. **日常**：起讫点分布较分散，大部分车次卖不满，以查询为主；
  2. **春运**：少数热门线路的需求远超运力，大量订单集中抢同一批车次日；
  3. **退票潮**：先卖到接近满座，再大量退票，同时继续卖票，座位区间高度碎片化。
- 每个场景分别用 **1、4、16 个压测线程**跑，共 9 组测量；每组跑 5 次，取中位数。
- 官方隐藏负载的规模大约是公开负载的 10 倍：约 2000 个站、120 条线路、每天 1 万个车次。

### 9.2 正确性门槛

- 一个场景中出现任何正确性错误（`query` 结果不一致、超卖或座位冲突、多程不原子、假阴性、重复退票成功、返回值非法、崩溃、超时、超内存），**该场景的 3 组测量全部记 0 分**。5 次重复中只要有一次出错就算错。
- ThreadSanitizer 报出数据竞争，或 `init` 超过 30 秒，**总分为 0**。

### 9.3 分数

- **性能分（90%）**：每组测量 = 0.7 × 吞吐分 + 0.3 × p99 延迟分，再取 9 组的平均值。
  - 每项都对标两个固定的参考实现：**基线**（一把全局锁加朴素扫描）记 0 分，**强参考**（出题方优化过的版本）记 100 分；
  - `分数 = 100 × ln(你的值 / 基线) / ln(强参考 / 基线)`，延迟一项用 `基线 p99 / 你的 p99` 代入；
  - 低于基线记 0 分，**高于强参考不封顶**。
- **偏好分（10%）**：每轮并发压测结束后，会用单线程补发一批订票请求（静默阶段）。取 1 个压测线程那一轮（结果完全确定）的静默阶段，分别统计靠窗满足率和同行满足率，各占一半，与参考贪心策略跑同一脚本的满足率对比，按比例折算，同样不封顶。
