# LLMBench 设计文档

LLMBench 是一个评测 LLM Agent 工程能力的框架：给 Agent 一份规格和固定的工具链，限时让它从零写出一个程序，再用独立的压测器和裁判打分。

第一道题是**铁路订票系统**（`tasks/railway/`）。本文记录这道题经过逐条讨论后确定的全部设计决策。面向 Agent 的规格见 [`tasks/railway/TASK.md`](../tasks/railway/TASK.md)；两者冲突时以 TASK.md 为准，并应同步修正本文。

参考资料：[meow-ai-arena / warehouse](https://github.com/chen-006/meow-ai-arena/tree/main/warehouse)。我们沿用了它“固定编译命令 + 隐藏负载 + 对数加速比计分”的思路，并针对它的已知问题做了改动：隐藏负载不公开、计分对标固定参考实现而不是其他参赛者、正确性用不变量裁判而不是逐字节比对（因为我们要考并发）。

---

## 1. 题目

| 维度 | 决策 |
|---|---|
| 形态 | **服务模式**，考并发。选手实现进程内 C++ 接口，压测器多线程直接调用 |
| 区间票 | 支持。同一座位可按不重叠区间多次出售；一程之内乘客全程坐同一座位 |
| 换乘 | 系统规划，换乘次数最少优先；最多换乘 2 次（3 程）；同站换乘，最短换乘 30 分钟 |
| 时刻表 | 每个车次有固定时刻表，每天相同；预售 3 天（第 0、1、2 天），库存按“车次日”独立 |
| 车型 | 统一 8 节编组，每车次日 578 座（见下表） |
| 规模（隐藏负载上限） | 约 2000 站、120 条线路（含若干孤立线路）、每天 1 万车次（快慢车，停站子集不同），单车次停站 ≤ 60 |
| 跨线车次 | 约 12% 的车次（`cross_line_permille = 120`）沿一条线路跑到换乘站（必停），再转入另一条线路继续运行，只跨两条线、不掉头、不重复经过同一站；对乘客是一程。接口不变，`Train::line` 只是始发线路；世界文件升到版本 2，车次记录列出 1–2 条线路供校验 |
| 公开负载 | 规模约为隐藏负载的 1/10 |

| 车厢 | 席别 | 布局 | 排数 | 座位数 |
|---|---|---|---|---|
| 1 | 商务座 | 2+1：`A │ C F` | 8 | 24 |
| 2–3 | 一等座 | 2+2：`A C │ D F` | 13 | 每节 52，共 104 |
| 4–8 | 二等座 | 3+2：`A B C │ D F` | 18 | 每节 90，共 450 |

座位号显示格式：`05-12F`（车厢-排号字母）。

停站上限 ≤ 60 是有意为之：每个座位的占用区间能压进一个 `uint64_t` 位图，奖励想到这个技巧的模型。

**线网生成**：新线路按“优先连接”挂到已有换乘站上（`hub_bias`，权重随该站已有线路数线性增长），形成枢纽但不会塌缩成少数超级枢纽；站点热度按规模（线路数 × 车次数）排名后服从 Zipf 分布，需求集中在大站。隐藏规模下实测：约 190 个换乘站，查询结果约 4–6% 为空（含孤立线路，属设计内），12–15% 的最优方案需要换乘 2 次。

## 2. 接口语义

接口头文件：[`tasks/railway/include/ticket_system.h`](../tasks/railway/include/ticket_system.h)。

- **标识符**：站点、线路、车次都是稠密 `uint32_t`（`0..N-1`）；名字只用于显示。车次日 = `(train, day)`。
- **时间**：分钟数。时刻表相对车次发车日 00:00，可超过 1440；请求和返回里用绝对分钟（第 0 天 00:00 起）。
- **`query`**：只看时刻表，不看余票，结果完全确定。
  - 首程上车时间落在 `[earliest, earliest 所在日的 24:00)`；所有程的车次日都在预售期内。
  - 同站换乘，下一程发车 ≥ 上一程到达 + 30 分钟；起点、各换乘站、终点两两不同；同一车次日不能重复。
  - 去重：车次日序列相同的方案只保留换乘最早的那个。
  - 排序：换乘次数 ↑ → 最终到达 ↑ → 首程发车 ↓ → 车次日序列字典序 ↑。返回前 K 个，K ≤ 5。
- **`book`**：订明确的方案（每程给出车次、日期、上下车站），多程原子执行，任何一程不够就整单失败并回滚，不自动换方案。一单 ≤ 5 人、同一席别。
- **拒售**：`SoldOut` 必须属实（假阴性判错）；座位够但引擎按售票策略不卖时返回 `Withheld`，不改变状态，不判错，只影响满足率和周转量（第 4 节）。
- **座位偏好是软约束**：偏好不影响能否出票。靠窗 = A 或 F；同行 = 同车厢同排且在同一侧连续（人数超过一侧座位数时退化为同排）。按满足率计入质量分。
- **`refund`**：只支持整单退票，不做改签。不存在或已退的订单返回 `NotFound`；并发退同一单恰好一个成功。
- 请求和返回都是 POD 结构体，返回错误码，不抛异常，压测器调用路径上不分配内存。

## 3. 负载与测量

- **用户意图脚本**：购票意图 = 查询 → 订第 1 个方案 → 失败则订下一个 → 直到成功或试完；另有纯浏览、随机退票（从全局成功订单池抽取，制造跨线程竞争）、重复退票、非法请求。`query` 结果由参考实现离线预算，压测器运行时只做极轻的决策。
- **三个场景**：
  1. **日常**：OD 按 Zipf 分布，多数车次卖不满；查询约 70%、订票约 25%、退票约 5%。
  2. **春运**：少数热门线路和车次日的需求远超座位数（强参考约一半的购票买得到），大量售罄，考热点锁竞争和售罄判断。长途旅客从热门线路起点附近的几站出发；起点还有一段客流很大的短区间（`corridor_permille` / `corridor_stations`，类似“上海—苏州”），短区间票占用的座位过了短区间终点很少有人接着坐，于是“多卖短途、服务更多人”和“留给长途、运更多里程”形成真实的取舍（见第 4 节）。隐藏负载的热门线路数按世界规模放大（120 条线里 10 条），使拥挤程度和公开负载一致。
  3. **退票潮**：先卖到接近满座，再大量退票同时继续卖票，考碎片区间复用和偏好。
- **闭环压测**：每个压测线程拿一条预生成的意图序列，调用一次、记一次时间窗、马上发下一个。
- **环境**：4 个物理核（只用大核，不算超线程）；三档并发度 1 / 4 / 16 线程。3 场景 × 3 档 = 9 组测量。
- **重复**：每组测量最多跑 5 次，吞吐和 p99 取中位数；任何一次出现正确性错误都按错误处理；每次运行重新启动进程。**自适应**：每组先跑 1 次，若这次性能分为 0（比基线慢或超时）或单次超过 2 分钟，就不再重复。
- **超时**：每组测量的超时 = 该组基线耗时 × 1.2 + 30 秒。超时只让这一组测量记 0 分，不算正确性错误，不连坐同场景其他线程档（比基线还慢本来就是 0 分，截断不损失信息）。
- **规模校准**：负载条数校准为 daily 40 万、spring 和 refund_wave 各 60 万（在 2.1 GHz Xeon 上实测外推：基线每次约 5–10 分钟，强参考每次几秒）；一个参赛单位最坏约 1 小时机器时间，快的约 10–15 分钟。
- **锚点**：强参考每组跑 3 次取中位数；基线每组只跑 1 次——它串行处理每个调用，波动很小，而每次要几分钟；基线误差 5% 只让分数偏移约 1 分。`prepare` 中不计时的步骤（生成负载、标准答案）并行执行，计时的锚点测量始终一次只跑一个。
- **资源**：选手内存预算 1.5 GB（进程总上限 = 1.5 GB + 压测器自身固定占用），超限按崩溃处理；`init` 上限 30 秒。

## 4. 裁判与评分

**正确性门槛（一票否决）**，以下任何一项出现，该场景 3 组测量全部 0 分：

- 超卖 / 同一座位区间重叠；多程订单非原子；
- `query` 结果与参考实现不一致；
- 假阴性：返回 `SoldOut` 时，其调用时间窗内不存在任何时刻真的不够座位（并发阶段，保守判定）；静默阶段（并发结束后单线程补发）里，按引擎**自己的**座位状态精确判定，有座却回 `SoldOut` 即为错误。注意不能拿静默阶段的结果去和参考实现逐条比对：有区间票时，后续订单能否成功取决于此前选了哪些座位，两个都正确的引擎完全可能给出不同结果；
- 同一订单退票两次都成功；崩溃、超内存。

另外：**TSan 报出数据竞争 → 总分 0**；**`init` 超过 30 秒 → 总分 0**。

**一轮测量的三个阶段**（由 `railbench_<引擎>` 执行，`railjudge` 离线判定）：

1. **并发阶段**：按 1 / 4 / 16 线程闭环压测，计时并记录每次调用的时间窗、状态和结果（查询结果记哈希，成功订单记座位）。只有这一阶段计入性能分。
2. **静默阶段**：单线程补发一批购票意图；按引擎自己的座位状态精确判定假阴性；1 线程那一轮的静默阶段用于偏好分。
3. **审计阶段**：单线程，对失败的多程订单和被退订单的每一程区间反复订票直到售罄（最多 500 个区间）。只看并发结果时，“回滚或退票时丢了座位”这类错误几乎发现不了：被丢的座位只有在同一车次日、同一区间后来恰好售罄时才会暴露。审计把这类错误变成精确的假阴性。

**变异测试**（`tasks/railway/tests/mutants/`）：在基线外面包一层，注入一种典型错误，裁判必须全部抓到。

| 变异 | 注入的错误 | 被抓到的方式 |
|---|---|---|
| `steal_seats` | 售罄时偷偷退掉别人的订单再卖 | 超卖 |
| `fake_sold_out` | 每 7 次订票谎称售罄 | 假阴性 |
| `busy_sold_out` | 有其他调用在进行时就回售罄（只在并发下出错） | 并发阶段的保守假阴性判定；单线程时正确通过 |
| `partial_book` | 多程逐程订，失败不回滚 | 审计阶段的假阴性 |
| `leaky_refund` | 多程订单退票只释放第一程 | 审计阶段的假阴性 |
| `double_refund` | 同一订单第二次退票也成功 | 退票检查 |
| `wrong_query` | 交换前两个换乘方案 | 查询比对 |
| `bad_seat` | 一等座偶尔给出不存在的 B 座 | 座位检查 |
| `data_race` | 无同步的全局计数器 | TSan 构建下压测直接失败 |
| `withhold_long` | （合法）按乘车时长和满座程度拒售，返回 `Withheld` | 必须**通过**裁判；评测冒烟测试另用“全部拒售”的实现确认满足率门槛会清零 |

**总分 = 75% 性能分 + 15% 周转量分 + 10% 偏好分**（公式在 [`eval/scoring.py`](../tasks/railway/eval/scoring.py)，评测和工作区的 `make score` 共用）。和强参考完全一样的实现得 95.5 分。

**性能分（75%）**：9 组测量各自计分后取平均。

- 每组 = 0.7 × 吞吐分 + 0.3 × p99 延迟分；
- 对标两个固定参考实现：**基线**（全局大锁 + 朴素扫描）= 0 分，**强参考**（我们优化的版本）= 100 分；
- `分数 = 100 × ln(x / 基线) / ln(强参考 / 基线)`，低于基线记 0，**高于强参考不封顶**；
- 吞吐 `x` = 并发阶段的调用总数 ÷ 挂钟时间；
- 延迟分的 `x` = **查询和订票两个 p99 改善倍数的几何平均**，即 `√((基线查询 p99 / 选手查询 p99) × (基线订票 p99 / 选手订票 p99))`；锚点同样这样计算。分开取 p99 是因为查询约占调用的 70%，混在一起的 p99 几乎看不出订票（春运热点）的尾延迟；退票量太少、p99 噪声大，不计入。

**偏好分（10%）**：取 **1 线程那一轮**（完全确定、可复现）的静默阶段，统计靠窗满足率和同行满足率（各占一半），与强参考的贪心策略跑同一脚本得到的满足率对比，线性折算，不封顶。

**订票质量**（裁判 `quality` 字段，取 1 线程那一轮的主阶段，退掉的订单不算）：

- **订票满足率** = 买到票的购票请求 ÷ 查询到至少一个方案的购票请求。**不计分，只作门槛**：低于强参考的 85%，该场景的性能、周转量、偏好全部记 0。正常出票的实现都在 99% 以上，门槛只挡大量拒售（例如用 `Withheld` 换吞吐，或一律不卖短途）。
- **旅客周转量（15%）** = Σ 买到票的请求的“人数 × 乘车分钟”。乘车分钟按请求**第一个查询方案**计，与实际订到的方案无关，堵住“拒售快车、把旅客挤到慢车上”刷分。记 r = 周转量 ÷ 强参考：r = 1 得 70 分，r ≤ 0.93 得 0 分，r ≥ 1.03 得 100 分，分段线性；三个场景取平均。
- **利用率**（只展示）= 拒绝过订票（短缺的程或 `Withheld` 的每一程）的“车次日 × 席别”上，卖出的座位分钟 ÷ 运力。

为什么这样设计（实验见 `tests/mutants/mutant.cpp` 的 `withhold_long` 和 `railgen` 的短区间参数）：

- 选座策略对满足率几乎没有影响：从 best-fit 到故意 worst-fit，满足率只差 0.1–1.3 个百分点。旅客失败后会改订其他车次，碎片化的损失被吸收了。所以满足率当计分项会让人人白拿，只适合做门槛。
- 早期的春运热门需求全是端到端长途，任何限售策略都只会两项同降。加入起点短区间客流、并让长途旅客只从前两站出发后，取舍才成立：以公开春运为例，“车次日卖出超过 30%/50%/70%/90% 后拒售短区间票”的周转量分约为 100/92/84/81，满足率基本不变；“一律不卖短区间票”周转量 +19%，但满足率只有强参考的 83%，被门槛清零。正常出票的引擎在 63–74 分之间，差异来自选座造成的碎片。
- 压力过大（热门占购票 90%）时“一律不卖”的满足率回到 85% 以上，门槛失效；热门线路过多则客流被摊薄、策略收益变小。公开与隐藏配置都选在两者之间。

## 5. 防作弊

| 类别 | 手段 | 对策 |
|---|---|---|
| 骗正确性 | 永远回“无票”、超卖、回执造假、退票不释放 | 时间窗假阴性检查 + 静默阶段比对；区间重叠检测；回执逐项校验 |
| 骗计时 | `init` 偷跑、跨次缓存、偷开线程、识别评测模式 | `init` 设上限；每次全新沙箱、只读文件系统；cpuset 固定核数；隐藏负载现场生成、ID 随机化 |
| 骗数据 | 对公开负载过拟合 | 隐藏负载规模和分布不同，参数不公开，种子评测时生成、赛后公开 |
| 骗环境 | 读裁判目录、联网、`fork` 常驻、数据竞争 | bubblewrap / nsjail + seccomp + cgroup；TSan 门槛；多次重复任一错即错 |
| 骗出题人 | 改本地工具、偷看参考实现 | 官方环境从源码重新编译，只认 `src/`；工作区只给去符号的二进制工具 |

**压测器与选手代码同进程**：压测器与 `src/*.cpp` 静态链接成一个可执行文件，日志在同一进程内存里，恶意代码理论上可以改写日志。不拆成两个进程，因为跨进程计时会给每次调用加上约 0.2–1 µs（强参考一次调用只要几 µs），而且 16 线程挤在 4 核上靠自旋等待，测出来基本是调度噪声。改用两道检查：

1. **自动静态扫描**：评测前扫描 `src/`，出现内联汇编、裸系统调用、`dlsym` / `dlopen`、读取 `/proc/self`、引用压测器符号、`mprotect`、可疑的内存遍历等就标记；成绩照出，但标注“待人工复核”。
2. **人工复核**：排行榜前几名和所有被标记的提交，人工阅读源码。

编译：官方命令固定为 `g++ -O2 -std=c++20 -pthread`；**允许**源码里用 `#pragma GCC optimize/target`；禁止内联汇编发起系统调用；只能用 C++ 标准库和 pthread。

## 6. Agent 规则

- **从零开始**：工作区包含 `TASK.md`、只读接口头文件、能编译的空实现、二进制本地压测器与裁判（另有 TSan 版压测器库和小负载，`make tsan`）、`query` 比对工具、公开负载生成器和公开负载；不给基线源码。
- **估分**：`make score` 用官方公式（`scoring.py`，随工作区发放）在公开负载上 1/4 线程估分。打包时在同一台机器上测一次基线和强参考，只发数值（`data/anchors.json`），不发强参考代码；约多花 10 分钟，`--anchors none` 可跳过。
- **硬时限 2.5 小时**（挂钟），到点终止会话，以终止时的 `src/` 为准。
- **每 30 分钟快照** `src/`，赛后逐个评测，画出分数随时间变化的曲线；排名只看最终版本。
- **参赛单位是“模型 + variant + 工具”**（如 `anthropic/claude-x (high) · Claude Code`）。禁止联网（沙箱强制）；只用标准库和 pthread；允许子 Agent 和并行，记录 token 与费用，排行榜额外展示“分数 / 美元”；不允许向人求助。
- **运行次数**：每个参赛单位至少 1 次，推荐 3 次；排行榜标注次数 n，按平均分排序，并展示最好、最差、每次运行和通过率。
- **运行方式**：OpenCode 自动运行（`run_opencode.py`）或人工模式（`run_manual.py`，任意工具，操作者只能原样粘贴运行器给出的提示词、时间提醒和续跑语）。两者进同一张榜，人工运行标注“人工”。
- **时间信息**：提示词写明开始和收卷时间；第 30/60/90/120 分钟和收卷前 10、2 分钟发同样的时间提醒；`make time`、`make check`、`make bench` 都显示剩余时间。

## 7. 平台与工程

- **官方评测在 Linux**（完整沙箱 + TSan）。**Windows 是一等公民的开发和自测平台**：MinGW-w64 g++，编译参数与 Linux 一致；工具链提示“非官方成绩”；需要 TSan 时可在 WSL2 中自测。
- **技术栈**：

  | 组件 | 语言 | 说明 |
  |---|---|---|
  | 压测器 | C++ | 与选手 `src/*.cpp` 静态链接成同一可执行文件，通过工厂函数拿实例 |
  | 裁判 | C++ | 离线读取压测器的原始日志校验，压测过程中不做校验 |
  | 负载生成器 | C++ | 自实现 xoshiro256** 与各种分布，全程整数运算，保证跨平台逐字节一致 |
  | 参考实现（基线、强参考） | C++ | 与选手同一接口 |
  | 评测编排 | Python | 沙箱、重复、算分、快照评测、报告 |
  | 构建 | CMake | 只用于我们的工具；选手代码用一条固定的 `g++` 命令编译 |

- **评测编排**：`tasks/railway/eval/railway_eval.py`。`prepare` 生成一季的数据、参考答案（强参考）、压测器自身内存占用（用空实现实测）和锚点（基线、强参考各 9 组）；`evaluate` 对一份提交依次做静态扫描、按官方参数编译、TSan 检查（3 个场景各一份小负载、4 线程）、9 组测量（自适应重复、超时、内存上限）并计分；`snapshots` 对中间快照走精简流程、最后一张走完整流程。每次运行在 `bwrap` 沙箱中（`--unshare-all`、无 `/proc`、只读挂载、私有 `/tmp`），由沙箱内的 `railexec` 把真实退出状态和峰值内存通过专用管道报告出来（隔着 `bwrap` 时 `wait4` 只能看到 `bwrap` 自己）。
- **机密材料**：
  - 强参考实现放在**单独的私有仓库**，以子模块引入，将来公开主仓库时不必改历史；
  - 隐藏负载不入库，只入库生成器；隐藏配置放在私有仓库的 `railway/hidden/`，种子评测时生成、赛后公开；
  - 打包使用白名单，CI 扫描打出来的包，确认除接口头文件外没有任何源码。

## 8. 参考实现

| 实现 | 位置 | 作用 |
|---|---|---|
| 判定基准（oracle） | `tasks/railway/reference/oracle/`（公开） | `query` 穷举所有候选再排序，不做任何剪枝，只用于交叉比对；太慢，不当锚点 |
| 基线 | `tasks/railway/reference/baseline/`（公开） | 性能分 **0 分锚点**：每个调用都拿同一把全局锁（含 `query`）；座位用区间列表、首个可用；`query` 逐层找前 K 个并按到达时间剪枝，每次查询临时标记能到终点的车次，无预计算索引 |
| 强参考 | 私有子模块 `private/railway/strong/` | 性能分 **100 分锚点**：直达连接索引 + 剪枝；每座位一个 `uint64_t` 区间位图、每车次日一把锁、分片订单表；偏好分的参考贪心；离线预算负载的 `query` 答案 |

基线和强参考的 `query` 都必须与判定基准逐字节一致（`ctest` 中的 `rail_crosscheck_*`）。单线程下实测强参考比基线快：公开规模 53–93 倍，隐藏规模 44–69 倍（三个场景）；多线程下基线因全局锁无法扩展，差距会更大，由里程碑 3 的并发压测器实测。

`railrun_<引擎> verify` 用独立的座位模型单线程重放负载，检查请求校验、座位合法性、区间冲突、精确假阴性和退票语义，是裁判确定性部分的雏形。

## 9. 里程碑

1. **规格与数据**：`TASK.md`、`ticket_system.h`、世界数据格式、负载生成器。
2. **两个参考实现**：基线与强参考，`query` 独立实现后在大量随机负载上交叉比对，消除规格歧义。
3. **压测器与裁判**：原始日志格式、安全性 / 原子性 / 假阴性 / 静默阶段 / 偏好统计；**变异测试**（超卖、永远无票、多程不回滚、数据竞争、重复退票成功的坏实现都必须被抓到）。
4. **评测编排**：沙箱、5 次重复、算分、快照评测、报告。
5. **打包与试跑**：打包工作区，用便宜的模型完整跑一次 2.5 小时，校准时限、规模和参考分数线。工具见 `tasks/railway/agent/`：`package_workspace.py`（白名单打包，预编译压测器库）；`run_opencode.py`（通过 OpenCode **v2 HTTP API** 运行：工具权限交给 OpenCode 的权限配置，禁止网页抓取和搜索、禁止向人提问、文件工具不能出工作区；网页界面监听 `0.0.0.0` 并强制密码，供人实时观看；运行器负责每 30 分钟快照、把当前时间和剩余时间插进会话、`make submit` **提前交卷**、到点先中断会话并杀掉全部进程再拍最后一张快照的**强制收卷**、未交卷停下时续跑、统计 token 和费用）；两种模式：试跑模式只靠 OpenCode 权限配置，正式模式（`--strict`）另加专用账户和 `vm_netguard.sh`，因为权限配置拦不住 `bash` 联网或读取工作区外的文件；同时支持 OpenCode 1.x 和 2.x，2.x 下 Agent 的 shell 环境被换成最小环境，读不到 API 密钥）；`run_manual.py`（人工模式，见第 10 节）；`run_reference.py`（用参考实现代替 LLM 空跑整条流程）。

Windows 支持贯穿 1–3：CI 同时跑 Linux 和 Windows，保证生成器两边产出逐字节一致。

## 10. 报告与人工模式

**人工模式**（`tasks/railway/agent/run_manual.py`）：为 OpenCode 以外的 Agent 工具（Claude Code、Codex CLI、Cursor 等）准备。运行器管规则，操作者只转发文本：

- 运行器准备工作区，操作者按 Enter 后开始计时，给出带时间的标准提示词（`prompt.txt`，并放进剪贴板）；
- 时间提醒和续跑语与 OpenCode 运行逐字相同，到点时响铃打印，操作者原样粘贴；续跑由操作者在运行器终端按 `r` 触发，最多 20 次；
- `make submit` 交卷；到点立即拍最终快照，以它为准；正式模式杀掉专用账户的全部进程，试跑模式可选 `--on-deadline` 命令；最后把 `src/` 设为只读；
- 工具名用规范名称表（`taskinfo.TOOLS`），避免同一工具被拆成几组；
- 用量可手填，会话记录可导入（`attach`）。

**统一会话格式**（`tasks/railway/agent/transcript.py`，`llmbench-transcript/1`）：按时间排序的事件（用户消息、模型步骤及其 token 与费用、工具调用及其输入、输出、退出码）。目前有 OpenCode 和 Claude Code 两个转换器；其他工具拿到真实日志样本后再补。报告只读这一种格式。

**报告**（`tasks/railway/report/report.py`）：读一个赛季和若干运行目录，生成静态网站目录：`index.html` 是排行榜，`runs/<运行>.html` 是每次运行的详情页。每页自包含，不访问网络，深浅色跟随系统并可切换，适配手机宽度。

- **只给标准运行排名**：正式模式、时限 150 分钟、用本赛季评分（评测结果里的赛季指纹 = `anchors.json` 的哈希）、最终快照是完整评测且有沙箱、任务包版本（`TASK.md`、提示词、接口、工作区 Makefile、公开配置的哈希）和提示词与赛季一致。其他运行进“非标准运行”区并写明原因；参考实现空跑和未评分的运行单独列出。
- **排行榜**：点加误差线（平均分、最差到最好、每次运行一个刻度，被正确性闸门清零的运行画空心），0 和强参考总分（95.5）两条参考线，坐标轴随最高分延伸；可排序的汇总表（平均 / 最差 / 最好、性能、周转量、偏好、通过率（被正确性或满足率门槛清零的测量记为不通过）、用时、结束方式、费用、分 / 美元、token、工具版本，混用版本时提示）；分项热力图；分数与费用散点图；各组平均分随时间的曲线；赛季信息和锚点。同一参赛单位在所有图里颜色一致。
- **详情页**：概览和致命错误横幅；快照得分曲线（标出时间提醒、续跑和交卷 / 收卷）；Agent 自测的 `make check` 公开场景吞吐（只用于解释，不计分）；9 组测量（吞吐、p99、init、峰值内存、每次重复）与锚点对比；延迟 CDF 和压测期间的吞吐（裁判输出的对数分桶直方图和 50 段时间片，参考实现的同类数据在 `prepare` 时保存）；正确性、订票质量（满足率与门槛、周转量及其得分、利用率、拒售次数，与强参考对比）与偏好；Agent 活动泳道图、上下文大小、累计费用、模型生成与工具执行的时间占比、缓存命中率、编译错误；代码演变（每张快照的行数和启发式并发策略指纹、相邻快照的 diff、最终源码）；精简会话记录（工具输出保留前后各 20 行，`--full-transcript` 保留全部）。
- **脱敏**：`--env-file` 里的值、运行的网页密码、形如常见 API 密钥的字符串一律替换为 `***`。
- **数据来源**：`railjudge` 输出延迟直方图（每个 2 的幂 4 个子桶）和 50 段吞吐时间片；`railway_eval` 记录峰值内存、每次重复的原始值、分布、编译时间和二进制大小、赛季指纹、机器信息；运行器在 `run.json` 里记录任务版本、提示词哈希、机器信息和时间线事件。
